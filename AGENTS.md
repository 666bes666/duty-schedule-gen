# Инструкции для агентов duty-schedule-gen

## Обязательный SDD: запрет обхода

Любое изменение проекта выполняется только по SDD: сначала требования с ID,
критерии приёмки, plan, tasks, traceability и анализ, затем реализация и проверки.
Запрещены изменения кода, тестов, зависимостей, CI, конфигурации, документации и
самих правил вне этого процесса. Refactor, cleanup и hotfix не являются исключением.
SDD-документы разрешено создавать в draft/specified до реализации; исходники
в `specs/` не являются SDD-артефактом и не освобождаются от gate.

В planned-контракте `files` перечисляет точные пути области изменения без glob.
Каждый изменённый файл должен покрываться изменённым контрактом; посторонняя
спецификация не разрешает работу за её пределами. Перед коммитом проверяется
`uv run python scripts/check_sdd.py --staged`; перед push — `--base HEAD~1`
для committed diff либо `--base HEAD` до коммита. CI проверяет такой же scope.
Зелёный gate не заменяет соответствие поведения требованиям и содержательное ревью.

Холодный старт: [docs/cold-start.md](docs/cold-start.md). Полная карта:
[docs/project-index.md](docs/project-index.md). `uv run python scripts/project_context.py`
показывает live контекст; `--check` отвергает устаревший индекс.

## Контекст и обязательные правила

Перед изменением прочитайте [конституцию](.specify/memory/constitution.md),
[руководство SDD](docs/sdd.md) и документы выбранного изменения в `specs/`.
Учитывайте [CONTRIBUTING.md](CONTRIBUTING.md) и действующие CI workflows.

- Используйте Python 3.12+ и `uv`; не заменяйте его на pip или Poetry.
- Сохраняйте существующие границы планировщика, API, CLI, UI и экспорта.
- Не добавляйте `#`-комментарии в исходный код. Пояснения решений размещайте в
  спецификации или плане; docstrings не обязательны.
- Новая функциональность требует тестов; минимальное покрытие — 80%.
- Имена событий логирования — английский `snake_case`.
- Сохраняйте чужие незакоммиченные изменения; не выполняйте reset или stash ради
  инициализации SDD.

## Изменение начинается со спецификации

1. Изучите затронутую реализацию и существующие тесты. `ARCHITECTURE.md` — контекст,
   а `specs/000-baseline/` — запись наблюдений; ни один документ не заменяет проверку
   исходников и тестов.
2. Создайте или обновите отдельную спецификацию изменения: пользовательские
   сценарии, требования с устойчивыми ID, критерии приёмки, совместимость и границы.
   Существенные неизвестные уточняйте; прямое поручение пользователя не требует
   дополнительного согласования самого SDD-процесса.
3. Подготовьте `plan.md`, `tasks.md` и `traceability.json` до реализации. Привяжите
   требования к существующим или запланированным тестам. Сначала сформулируйте
   проверяемое поведение, затем выбирайте реализацию.
4. Проверьте согласованность спецификации, плана и задач (`speckit-analyze` или
   содержательное ревью). Выполните ограниченные, проверяемые задачи.
5. Запишите реальные команды, результаты и ограничения в `evidence.md`. Отмечайте
   задачи выполненными только после проверки. Статус `complete` требует закрытых
   задач, evidence и выполненных критериев приёмки.

Структура `traceability.json`, статусы и команды описаны в [docs/sdd.md](docs/sdd.md).
Проектные файлы в `specs/` и `.specify/` версионируются вместе с реализацией.
Локальный указатель `.specify/feature.json` не является источником истины для CI.
Для каждого агента задавайте `SPECIFY_FEATURE_DIRECTORY` и
`SPECIFY_FEATURE_NO_PERSIST=1`, чтобы не переключать активную спецификацию коллег.
При таком значении не записывайте `.specify/feature.json`, даже если skill
предлагает сохранить указатель.

GitHub Spec Kit закреплён на версии **1.1.3**. Codex использует `$speckit-*` из
`.agents/skills/`, Claude — `/speckit-*` из `.claude/skills/`. Не устанавливайте
расширение `git`: спецификации имеют собственные каталоги, feature-ветки не нужны.
Сгенерированные инструкции и шаблоны применяются с учётом правил этого проекта.

## Проверки и evidence

Перед push выполните:

```bash
uv run python scripts/check_sdd.py --base HEAD~1
uv run python scripts/project_context.py --check
uv run ruff check src/ tests/ scripts/
uv run ruff format --check src/ tests/ scripts/
uv run mypy src/ scripts/
uv run pytest tests/ -q --ignore=tests/ui
```

Для проверки SDD относительно выбранного исходного коммита используйте
`uv run python scripts/check_sdd.py --base COMMIT`. Любое изменение вне SDD-документов должно покрываться точным `files` scope
обновлённого planned-контракта. `--base` учитывает рабочее дерево и untracked;
`--staged` проверяет снимок Git index. Обновление только baseline не разрешает реализацию.

SDD gate проверяет структуру, ID, ссылки и сопровождение изменения артефактом.
Смысловое соответствие поведения требованиям проверяют тесты и ревью; зелёный gate
не является доказательством завершения фичи. Дополнительные security, performance,
UI и platform проверки выполняются по существующим уровням CI.

При изменении API-контракта обновляйте соответствующие требования, контрактные
тесты и `specs/000-baseline/contracts/openapi.json` после анализа совместимости.
Snapshot проверяет расхождение схемы OpenAPI, но не доказывает поведение API во
время выполнения и не заменяет тесты аутентификации, ошибок или бизнес-правил.

## Git и доставка

Обычная работа: **коммит напрямую в `dev` → push сразу после коммита → PR в `test`
→ PR в `main`**. Не создавайте feature-ветки и не меняйте ветку ради Spec Kit.
Перед коммитом проверьте текущую ветку и состав diff; сообщения — Conventional
Commits. Перед продвижением дождитесь зелёного CI; PR мержатся через GitHub.
Обычный push напрямую в `main` запрещён.

Существующее исключение для критического hotfix сохраняется: ветка от `main`, PR
в `main`, затем cherry-pick в `dev` и `test` с push. SDD-артефакт исправления и
проверки должны сопровождать hotfix.

## Поддержание контрактов

Сохраняйте ID требований при уточнениях; изменение смысла фиксируйте явно.
Feature-спецификации поддерживаются как живые контракты. При последующих изменениях
обновляйте затронутые требования, план, задачи и traceability, возвращая изменение
в подходящий незавершённый статус. Исторические результаты в evidence сохраняйте:
добавляйте новую запись с датой и результатом вместо переписывания старого исхода.
В baseline отражайте вновь проверенные факты и ограничения, а не обещания.
