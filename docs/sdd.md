# Разработка по спецификации (SDD)

SDD связывает ожидаемое поведение, реализацию и доказательства проверки.
Для каждого изменения сначала описываем требования и критерии приёмки, затем
планируем задачи, реализуем их и проверяем результат. Текущий продукт продолжает
использовать существующую архитектуру и pipeline `dev → test → main`.

## Где находятся документы

| Путь | Роль |
|---|---|
| `.specify/memory/constitution.md` | Правила, которым должны соответствовать планы и реализация |
| `.specify/templates/` | Шаблоны документов для нового изменения |
| `.agents/skills/speckit-*/` | Инструкции Spec Kit для Codex |
| `.claude/skills/speckit-*/` | Инструкции Spec Kit для Claude |
| `specs/000-baseline/` | Наблюдаемое существующее поведение и известные пробелы |
| `specs/NNN-change-name/spec.md` | Сценарии, требования с ID, критерии приёмки и совместимость |
| `specs/NNN-change-name/plan.md` | Решения, затронутые файлы, проверки и риски |
| `specs/NNN-change-name/tasks.md` | Проверяемые задачи с состоянием выполнения |
| `specs/NNN-change-name/traceability.json` | Статус и связь требований с тестами |
| `specs/NNN-change-name/evidence.md` | Выполненные проверки, результаты и ограничения |

Baseline фиксирует подтверждённые наблюдения и не является ретроспективным
обещанием, что вся система соответствует идеальной спецификации. Если документы
расходятся с реализацией, проверяем код и тесты, фиксируем расхождение и создаём
отдельное изменение для исправления. Не объявляем непроверенные сценарии закрытыми.

## Инструменты

Проект содержит scaffold **GitHub Spec Kit 1.1.3**; runtime приложения от него не
зависит. Общие сценарии находятся в `.specify/scripts/`, интеграции — в каталогах
skills. Git extension не установлен: toolkit создаёт каталог спецификации без
feature-ветки. Не устанавливайте его и не запускайте генератор в режиме, который
меняет текущую Git-ветку.

| Шаг | Codex | Claude |
|---|---|---|
| Конституция | `$speckit-constitution` | `/speckit-constitution` |
| Требования | `$speckit-specify` | `/speckit-specify` |
| Уточнения | `$speckit-clarify` | `/speckit-clarify` |
| План | `$speckit-plan` | `/speckit-plan` |
| Задачи | `$speckit-tasks` | `/speckit-tasks` |
| Анализ согласованности | `$speckit-analyze` | `/speckit-analyze` |
| Реализация | `$speckit-implement` | `/speckit-implement` |
| Проверка завершения | `$speckit-converge` | `/speckit-converge` |

Skills помогают подготовить документы; требования проекта из `AGENTS.md` и
конституции применяются и при использовании сгенерированных инструкций.
Не переинициализируйте scaffold с `--force` без просмотра конфликтующих файлов.
Обновление toolkit — отдельное проверяемое изменение с фиксированной версией.

## Новое изменение

1. Прочитайте конституцию, baseline, затронутую реализацию и тесты. Проверьте
   `git status` и текущую ветку: обычные изменения выполняются в `dev`.
2. Создайте каталог `specs/NNN-change-name/` через `speckit-specify`. Номер
   идентифицирует спецификацию, а не Git-ветку. Описывайте пользовательский результат,
   критерии приёмки, совместимость и исключения; детали реализации внесите в план.
3. Зафиксируйте требования с устойчивыми ID, например `EXPORT-001`, и уточните
   существенные неизвестные до зависящей от них реализации.
4. Создайте `plan.md` с точными файлами, решениями, рисками и проверками, затем
   `tasks.md` с задачами в формате `- [ ] T001 ...`. Маленькое исправление может
   иметь короткую спецификацию и несколько задач; отдельные research или data-model
   документы нужны, только если помогают проверить решение.
5. Добавьте `traceability.json`, проверьте согласованность документов, установите
   статус `planned` и запустите структурный валидатор. Запланированные тесты можно
   описывать в traceability до создания файлов. Реальные файлы и selectors
   обязательны для `complete` и baseline `recorded`.
6. Выполняйте задачи, добавляя соответствующие тесты и проверяя критерии приёмки.
   Обновляйте задачи и traceability вместе с реализацией; рабочий статус —
   `in-progress`.
7. Добавьте в `evidence.md` реальные команды, результаты, дату, ревью и известные
   ограничения. Закройте задачи и выставьте `complete`, когда критерии выполнены.
   Выполните обязательные локальные проверки, затем используйте обычную доставку.

При работе с существующим изменением задайте его каталог явно в том же терминале,
из которого запускается агент:

```bash
export SPECIFY_FEATURE_DIRECTORY="$PWD/specs/001-sdd-adoption"
export SPECIFY_FEATURE_NO_PERSIST=1
```

Для создания нового каталога без запуска агента доступен локальный helper:

```bash
bash .specify/scripts/bash/create-new-feature.sh --help
SPECIFY_FEATURE_NO_PERSIST=1 bash .specify/scripts/bash/create-new-feature.sh --dry-run --json --short-name csv-export "Добавить экспорт CSV"
SPECIFY_FEATURE_NO_PERSIST=1 bash .specify/scripts/bash/create-new-feature.sh --json --short-name csv-export "Добавить экспорт CSV"
```

Dry run показывает предлагаемые пути; следующая команда создаёт каталог и начальный
`spec.md`. Возьмите каталог файла `SPEC_FILE` из JSON-результата и задайте его в
`SPECIFY_FEATURE_DIRECTORY` перед следующими шагами. Helper версии 1.1.3 не
создаёт Git-ветку; флаг `--allow-existing-branch` исторически назван так, но означает
повторное использование существующего каталога. Для работы с готовой
спецификацией создание каталога повторно не требуется.

Для нового изменения замените путь на его каталог. Не используйте
`SPECIFY_FEATURE` как единственный указатель: он задаёт метку, а не путь.
`.specify/feature.json` — игнорируемый локальный указатель, который не требуется
коллегам или CI. При параллельной работе каждый агент выбирает собственный каталог;
`SPECIFY_FEATURE_NO_PERSIST=1` предотвращает перезапись общего локального указателя.

В таком режиме агент также не выполняет запись указателя из текста skill:
правила `AGENTS.md` и конституции имеют приоритет над этим шагом scaffold.

## Статусы и traceability

Пример для изменения:

```json
{
  "kind": "change",
  "status": "planned",
  "requirements": [
    {
      "id": "SDD-001",
      "tests": ["tests/unit/test_sdd.py::test_name"]
    }
  ]
}
```

`test_name` — пример: замените его на реальный проверяющий тест.
Каждый ID из traceability должен присутствовать в `spec.md`.

| Статус изменения | Что должно быть готово |
|---|---|
| `draft` | Первичный `spec.md` и traceability; вопросы и границы ещё уточняются |
| `specified` | Требования и критерии сформулированы |
| `planned` | Есть `plan.md`, `tasks.md` и связь требований с проверками |
| `in-progress` | Реализация идёт по плану; чекбоксы отражают проверенный прогресс |
| `complete` | Задачи закрыты, есть `evidence.md`, критерии приёмки проверены |

Baseline использует `"kind": "baseline"` и `"status": "recorded"`; к нему не
применяется жизненный цикл изменения. Сам статус — запись разработчика,
подлежащая проверке, а не автоматическое доказательство качества.

## Проверки

```bash
uv run python scripts/check_sdd.py
uv run python scripts/check_sdd.py --base COMMIT
uv run ruff check src/ tests/ scripts/
uv run ruff format --check src/ tests/ scripts/
uv run mypy src/ scripts/
uv run pytest tests/ -q --ignore=tests/ui
```

Замените `COMMIT` на исходный коммит проверяемого изменения. Без `--base` валидатор
проверяет документы; с ним дополнительно сопоставляет diff с SDD-артефактами.
При изменении `src/**`, `app.py` или `api_main.py` должен измениться хотя бы один
артефакт изменения (`spec.md`, `plan.md`, `tasks.md`, `evidence.md` или
`traceability.json`) со статусом `planned`, `in-progress` или `complete`.
Обновления только baseline недостаточно.

В `.github/workflows/sdd.yml` SDD-проверки работают для `dev`, `test` и `main`,
дополняя существующие уровни CI. Валидатор проверяет структуру, ID, существование
ссылок и сопровождение кода документами. Он не проверяет, действительно ли тест
доказывает требование, и не выявляет смысловое противоречие текста и реализации.
Это задача анализа согласованности, тестов и независимого ревью.

Контракт `specs/000-baseline/contracts/openapi.json` хранит текущую схему FastAPI.
`tests/contract/test_openapi_snapshot.py` обнаруживает расхождение схемы. При
намеренном изменении API обновите требования, тесты поведения и snapshot после
проверки совместимости. Snapshot не заменяет проверки auth, ошибок, rate limiting
и результатов генерации.

## Доставка и дальнейшие изменения

Коммитим напрямую в `dev`, запускаем проверки до push и пушим сразу после коммита.
Продвижение идёт через PR `dev → test → main` с зелёным CI. Spec Kit не меняет этот
порядок. Существующий hotfix-процесс описан в `CONTRIBUTING.md`.
В PR укажите спецификацию, затронутые ID требований и evidence.

Спецификации изменений — живые контракты: при изменении поведения обновляйте
затронутые документы и сохраняйте ID требований. Для нового самостоятельного
изменения создайте новый каталог и сослитесь на изменяемый контракт; старый
результат проверки не становится доказательством нового поведения.
Если ранее завершённое изменение продолжается, верните ему подходящий рабочий
статус и актуализируйте план и задачи. Исторические evidence сохраняйте и дополняйте
новой записью; baseline обновляйте только подтверждёнными фактами.
