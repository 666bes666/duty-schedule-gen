# Переход проекта на Spec-Driven Development

Дата: 2026-10-10. Тип: изменение процесса разработки. Статус: complete.

## Цель и границы

Разработчик и агент начинают изменение с проверяемого требования, получают план
и задачи, а завершение подтверждают тестами и записанными результатами. Переход
сохраняет текущую архитектуру приложения и маршрут `dev → test → main`.
Изменения алгоритмов, исправление найденных дефектов продукта, релиз и продвижение
в `test`/`main` не входят в этот переход.

## Требования и приёмка

- **SDD-001**: репозиторий содержит закреплённый GitHub Spec Kit 1.1.3,
  конституцию и интеграции Codex/Claude. Создание спецификации не переключает
  ветку `dev`; расширение `git` отсутствует. Проверка: запуск помощников
  в отдельном временном репозитории и проверка текущей ветки.
- **SDD-002**: существующее поведение записано в `000-baseline` с ID требований,
  ссылками на реальные тесты и отдельными известными пробелами. Baseline не
  означает полную приёмку продукта. Проверка: валидатор проверяет ссылки;
  независимое ревью сопоставляет утверждения с кодом и тестами.
- **SDD-003**: для изменений есть `spec.md`, `traceability.json`; с этапа
  planned — `plan.md` и `tasks.md`; для complete — `evidence.md` и закрытые
  задачи. Черновики и запланированные тесты могут быть незавершёнными.
  Некорректный JSON, статусы, ID, пути и отсутствующие документы дают ненулевой
  код завершения проверки.
- **SDD-004**: изменение `src/`, `app.py` или `api_main.py` требует изменения
  хотя бы одного артефакта связанной спецификации изменения на этапе planned
  или позднее. Baseline и черновик не заменяют спецификацию изменения.
  Проверка работает для push и PR во всех трёх ветках.
- **SDD-005**: текущая OpenAPI-схема сохранена как снимок и сравнивается с
  приложением контрактным тестом. Изменение схемы требует намеренного обновления
  снимка в рамках спецификации; известные несовпадения с runtime отражены в baseline.
- **SDD-006**: README, CONTRIBUTING, AGENTS и CLAUDE указывают на один процесс;
  PR содержит ссылку на спецификацию и результаты приёмки. Документация объясняет,
  что структурный CI не доказывает соответствие смыслу требований.

## Сценарии

1. Разработчик создаёт новую спецификацию, уточняет неоднозначности, составляет
   план и задачи, добавляет `traceability.json`. План может ссылаться на ещё
   не написанные тесты. Работа идёт напрямую в `dev`.
2. Агент реализует задачу, обновляет тесты и evidence. Complete допускается
   только с существующими доказательствами и закрытыми задачами.
3. Push меняет реализацию без артефактов изменения: SDD CI завершается ошибкой.
4. Push добавляет только черновик: структурная проверка разрешает незаконченный
   план, если реализация не меняется.

## Ограничения

Автоматическая проверка устанавливает структуру, корректность ссылок и факт
изменения feature-артефакта. Связь изменённого кода с конкретным требованием,
достаточность тестов и истинность evidence оцениваются при ревью. Тесты UI,
CP-SAT и PDF зависят от соответствующего окружения; пропуск теста не равен успеху.
