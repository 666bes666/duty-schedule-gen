# Нормы часов и качество графика

Дата: 2026-10-10. Исходный коммит: f4326134433c9b1e8daca0a598cd88698920b9a0.

## Контекст и цель

Изменение реализует согласованный итог продуктового интервью; общий контракт:
[решения](../004-scheduling-validity/decisions.md). Baseline описывает наблюдения,
а не гарантии; уточняемые ID: SCH-005, SCH-008, SCH-009, SCH-010.

## Пользовательские сценарии

### US1 — Составить график по выбранной норме часов (P1)

Пересекающиеся отпуск/больничный вычитаются один раз; явно выбранная полная норма не снимает запрет отсутствия. Р3/Р5 требуют подтверждения конкретного назначения и одинаково учитываются всеми потребителями; баланс сравнивает подходящие пулы.
Каждый сценарий связан с требованиями ниже и реальными тестами в traceability.

## Требования и критерии приёмки

- **HOURS-001**: Календарная норма — сумма 8/7 часов рабочих дат. Скорректированная норма вычитает объединение рабочих дат отпуска/больничного один раз; обычная недоступность не уменьшает норму. В ready фактические часы равны выбранной цели точно.
- **HOURS-002**: Составитель может явно выбрать полную календарную норму сотрудника/месяца после отсутствия; рассчитанная, выбранная и фактическая нормы отображаются отдельно. Работа в самом отсутствии остаётся запрещённой.
- **HOURS-003**: Индивидуальные часы Р разрешены в пределах обычной длительности дня с подтверждением конкретного назначения; обязательные дежурства не сокращаются. Все потребители учитывают одни и те же часы.
- **HOURS-004**: Для первого построения качество сравнивается по порядку: парные выходные вместо одиночных, короткие серии, баланс вечеров/ночей, баланс дежурств в нерабочие даты. Баланс оценивает текущий и предыдущий месяц, пропорционально выбранной норме внутри подходящих пулов каждого периода. В повторном расчёте существующей версии сначала минимизируются изменённые ячейки после hard rules/norm/pins; затем применяется этот порядок качества. Исторический priority не меняет согласованный порядок.

- **HOURS-005**: Аналитика и оптимизация обозначают фактическое окно и происхождение качества, различают месячную и boundary серию; отсутствие лога не означает отсутствие оптимизации. Сохраняются качество/число правок до и после. Deprecated priority не обещает изменения фиксированного порядка, поддерживаемые предпочтения имеют общий последний tie-break обоих алгоритмов. См. DATA-005 и QUALITY-003.

## Границы и совместимость

Сохраняются Python 3.12+, uv и границы модулей. Существующие списки смен и команды
сохраняются; новые поля добавляются с миграцией старых настроек. Ошибочное старое
поведение (фиктивные отсутствия, приблизительная норма, непроверенный экспорт)
меняется намеренно. Устаревшие входы без календаря/истории допускают диагностику,
но не автоматически пригодный результат. Изменения API отражаются в контрактных
тестах и OpenAPI snapshot. Доказательства старых изменений не переписываются.

## Проверка успеха

Все перечисленные требования имеют воспроизводящие тесты в traceability;
обязательные проверки проходят, ограничения записаны в evidence. Зелёный SDD gate
сам по себе не доказывает выполнение требований. Complete устанавливается после
реализации, независимого ревью и проверки критериев.


## Уточнение после аудита и интервью 013 — 2026-10-11

HOURS-004 явно изменён по ответу владельца: окно баланса теперь текущий и предыдущий месяц, а не только месяц расчёта. При первом построении порядок мягких целей сохраняется; в repair до этих целей минимизируются изменённые ячейки (016). Нормы/доступность учитываются для каждого подходящего пула и периода, missing history не подменяется нулём (017). HARD требования HOURS-001..003 сохранены.

Контракт после уточнения реализован вместе с 014–017. Результаты прежней реализации
сохранены в evidence; новые selectors проверены, результаты добавлены отдельно. Связи:
014 сохранность → 015 подготовка/восстановление → 016 repair → 017 качество.
