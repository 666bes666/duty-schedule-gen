# Критический аудит продукта

Дата: 2026-10-11. Проверено приложение 5.0.0 на dev,
SHA `f6fe168fbbc189a4d67a499de19c1be14bcd1e41`. Runtime не изменялся.
Отчёт предваряет интервью; предлагаемые решения ещё не являются согласованными
изменениями бизнес-правил. Процесс и состояние: [spec](spec.md), [tasks](tasks.md),
[evidence](evidence.md).

## Продуктовая оценка

У продукта есть полезная основа: независимая проверка готовности, точные часы,
календарь с происхождением данных, перенос через месяцы, ручные закрепления,
переносимый проект и три способа экспорта. Обычный экспорт повторно проверяет
график, а диагностический результат не выдаётся за готовый.

Самая слабая часть — путь человека через продукт. Составитель должен понимать
служебные настройки, несколько видов истории и подтверждений, причины
диагностического отказа и разницу между YAML, проектом и XLS. Сейчас правильность
проверяется лучше, чем помощь в достижении правильного результата. Есть также
конкретные потери данных и различия между интерфейсами, которые существующая
регрессия не обнаруживает.

794 runtime-теста и 7 UI-тестов прошли; application coverage 87,63% с исключением
UI из числового покрытия. Это подтверждает существующую регрессию и не отменяет
проблемы ниже. Основной UI journey использует заранее закреплённые назначения
и синтетический календарь; он проверяет взаимодействие, а не качество расчёта
неизвестного реального месяца.

## Подтверждённые дефекты

P1 здесь означает потерю данных, непригодный результат или ложное успешное
выполнение действия. P2 — неправильное объяснение результата или лишнюю работу.
Это приоритеты данного аудита, а не утверждение частоты проблем в реальной команде.

### PLOG-01 — Идентичность сотрудника ломается на границах UI и XLS (P1)

**Что проверено.** Переименовать M0 в пустую строку с сохранением employee_id в
готовом fixture `tests/ui/fixtures.py::journey_config/journey_days`, применить
`update_config`, затем `check_current`. Результат имеет `status=ready` и шесть
сотрудников. `export_xls` успешно создаёт файл, однако
`parse_carry_over_from_xls` возвращает **0** записей: первая строка с пустым именем
считается концом таблицы. Входная модель Employee не запрещает пустое имя.

Второй пример: имя `Иванов, Иван` сохраняет ready после переименования, но
`_edit_df_to_schedule(_schedule_to_edit_df(schedule), schedule)` без единой
пользовательской правки превращает готовый график в diagnostic. Редактор соединяет
имена запятыми и затем разбивает по запятой, создавая двух неизвестных сотрудников.

**Последствие.** Допустимый для одного интерфейса сотрудник становится
непереносимым в другом; можно потерять историю всей команды или испортить график
одним нажатием применения неизменённой таблицы.

**Источники.** `models.py::Employee`, `project.py::update_config`,
`ui/builders.py::_schedule_to_edit_df/_edit_df_to_schedule`,
`xls_import.py::parse_carry_over_from_xls`. Затронуты REV-002, UIC-001/UIC-003,
HIST-003; стабильный ID уже существует, но строковые назначения не используют
его на всех границах.

**Требование к исправлению.** Общая проверка непустого отображаемого имени;
редактор выбирает сотрудников по идентичности, а не разбирает их имена как
разделённый текст. Legacy-входы мигрируются явно. Приёмка: неизменённая таблица
и XLS round-trip сохраняют всех сотрудников с запятыми и допустимыми символами;
пустое имя отвергается до расчёта/экспорта, а не прекращает импорт молча.

### PLOG-02 — Сохранение исходной истории меняет невидимые данные (P1)

**Что проверено.** У M0 сохранено `consecutive_off=4`. Построить таблицу с теми
же значениями, которые показывает раздел «История», и без изменения вызвать
`ui/components.py::_carry_from_frame`. Получается `consecutive_off=1`.
Для рабочего последнего статуса `consecutive_same_shift` также устанавливается
в 1 вместо сохранённого значения; source становится manual.

**Последствие.** Сохранение истории одного сотрудника может перезаписать скрытые
счётчики остальных. Граница месяцев и оптимизация парных выходных начинают
использовать другие данные, хотя составитель их не менял. Общая проверка при этом
не знает, что исходная достоверная история была потеряна.

**Источники.** `ui/components.py::_history_configuration/_carry_from_frame`,
`models.py::CarryOverState`, `scheduler/postprocess/quality.py::quality_key`.
Затронуты HIST-002/HIST-003, UIC-001/UIC-002.

**Требование к исправлению.** Неизменённая строка сохраняет все счётчики,
идентичность, дату и источник; изменение одной строки не меняет остальные.
Смена последнего статуса должна запрашивать недостающие данные или явно
инвалидировать их. Приёмка включает импорт XLS → открыть «История» → сохранить
без правок и изменение только одного сотрудника.

### PLOG-03 — API сообщает об успешном what-if, хотя изменение проигнорировано (P1)

**Что проверено.** `VariantPatch` и `apply_patch` принимают
`{"solverr": "cpsat"}`. Конфигурация после применения полностью равна исходной.
POST `/api/v1/whatif/compare` отвечает HTTP 200, вариант получает
`status=success`. UI тот же верхнеуровневый неизвестный ключ отвергает.
Корневая модель Config также молча отбрасывает неизвестные поля.

**Последствие.** Опечатка в параметре может быть принята за проведённый
эксперимент. Пользователь делает вывод о сценарии, который фактически не проверялся.
UIC-004 обещает согласованный UI/API what-if, но проверки различаются.

**Источники.** `api/schemas.py::VariantPatch`,
`api/whatif_service.py::apply_patch`, `ui/views.py::_render_whatif_panel`,
`ui/components.py::WHATIF_PARAMETERS`, `models.py::Config`.

**Требование к исправлению.** Единый проверяемый список изменений для UI и API;
неизвестные пути отвергаются с указанием поля до расчёта. Различить изменение,
которое корректно применилось, но не изменило назначения, и изменение, которое
вообще не было принято. Nested-поля сотрудников тоже проверяются. Старые
неподдерживаемые YAML-поля требуют явной миграции/предупреждения, а не слепого
`extra=forbid` без анализа совместимости: в example есть `team_lead`.

### PLOG-04 — Противоречивый календарь объявляется корректным входом (P1)

**Что проверено.** В проверенной апрельской конфигурации поменять month на 5,
оставив полный календарь апреля. POST `/api/v1/config/validate` возвращает
HTTP 200, `valid=true`, пустые errors/warnings. POST `/api/v1/schedule/plan`
на том же входе возвращает **502 calendar_error** с причиной несовпадения периода.
Это несогласованные пользовательские данные, а не сбой внешнего источника.

**Последствие.** Клиенту сначала обещают корректный вход, затем он получает
ошибку внешнего сервиса и может бессмысленно повторять запрос. В UI аналогичный
календарь перехватывается как ошибка; контракт ошибок не един.

**Источники.** `models.py::Config/collect_config_issues`,
`api/routes/config.py::validate_config`, `api/planning.py::plan_schedule`,
`calendar.py::calendar_for_config`, `api/errors.py::handle_calendar_error`.
Затронуты SEC-002, TIME-001, VALID-001.

**Требование к исправлению.** Проверять связи периода и календаря до поиска.
Отдельно определять синтаксически корректный вход и готовность данных к расчёту.
Несовместимый пользовательский период получает согласованную ошибку входа либо
типизированную диагностику plan; настоящий сбой получения календаря сохраняет
свою причину. Точный HTTP-контракт выбирается с анализом совместимости.

### PLOG-05 — Лог оптимизации даёт ложное объяснение (P2)

**Что проверено.** Готовый fixture без pins, seed=0, стандартный
`optimize_candidate` с budget=120 меняет назначения. Первый компонент quality_key
уменьшается 77 → 52; следующий компонент растёт 500266 → 600371, что допустимо
при согласованном порядке целей. В результате нет metadata.changelog.
`ui/views.py::_render_changelog` при этом выводит:
«Лог оптимизации пуст — постобработка не внесла изменений».

**Последствие.** Пользователь получает неверное объяснение реального результата
и не видит, чем пожертвовали ради парных выходных. Отсутствие сохранённого лога
ошибочно трактуется как отсутствие изменений.

**Источники.** `scheduler/postprocess/quality.py::optimize_candidate`,
`ui/views.py::_render_changelog`, действующий core vs отдельно сохранённый pipeline.
Затронуты HOURS-004, UIC-003.

**Требование к исправлению.** Сохранять происхождение и изменения действующего
алгоритма либо честно обозначать недоступный лог. Показать качество до/после
и критерии, которые ухудшились. Сам порядок приоритетов из решений 004 сохраняется.

## Пробелы контрактов и качества продукта

### PLOG-06 — Значение нескольких настроек не определено для всех алгоритмов (P2)

Все четыре optimization_priority на одном незакреплённом входе дают ready и
одинаковые назначения. Действующие core/quality/solver этот параметр не используют;
старый отдельный pipeline его использует, но не является генератором продукта.
preferred_shift входит в последний уровень выбора greedy, однако отсутствует
в целевой функции CP-SAT. Смена всех московских предпочтений утро ↔ вечер
в воспроизведении CP-SAT также не меняет назначения.

`Config.timezone="Wrong/Zone"` принимается, тогда как ICS использует фиксированные
зоны городов и дежурства МСК. Фиксированное время согласовано в 004 и само по себе
правильно; редактируемое поле «Часовой пояс календаря» создаёт другое ожидание.

Это не доказательство нарушения нового фиксированного порядка HOURS-004:
контракт не обещает действие исторического optimization_priority. Проблема —
сохраняемые и предлагаемые параметры без явного описания эффекта/совместимости.
Нужно явно определить поддерживаемые параметры, deprecated-поля, силу предпочтений
и понятное поведение каждого алгоритма. Не обещать одинаковые назначения;
обещать одинаковое значение входных правил и объяснимую разницу поиска.

### PLOG-07 — Аналитика и проверка считают серию по разным окнам (P2)

Готовый вход: до месяца M0 уже работал 2 дня, затем работает первые 3 дня.
Реальная серия на границе — 5; compute_stats показывает max_streak_work=3.
Общая проверка и quality_key учитывают предыдущие дни, статистика — только месяц.
Одиночные выходные на границе также оцениваются разными методами.

Месячная метрика сама по себе допустима, но её окно не обозначено в UI и what-if;
составитель может принять её за тот же показатель, которым проверяют ограничение.
Нужно различить «внутри месяца» и «с учётом исходной истории» и использовать
согласованные показатели в объяснении качества. Затронуты HIST-001/HOURS-004/UIC-003.

### PLOG-08 — Повторная проверка засоряет историю версий (P2)

На неизменённом готовом проекте три check_current увеличивают число ревизий
с 1 до 4. `_append_revision` всегда создаёт новую ScheduleRevision, включая
проверку без изменения исходных данных/назначений. На открытии каждая сохранённая
версия проверяется заново; редактор сравнения получает шумные одинаковые версии.

REV-001 требует версии для правок, но не определяет идентичное сохранение,
повторную проверку, откат и причины ревизий. Нужно отделить результат проверки
от изменения графика, сделать повторное действие идемпотентным либо явно вести
отдельные события проверки. Порог размеров/скорости открытия пока не измерялся.

### PLOG-09 — Незагруженная в файл работа исчезает после перезагрузки (P1: риск процесса)

В реальном браузере первый расчёт создал текущую диагностическую версию.
После reload этой версии и её заголовка нет, приложение показывает начальный
состав и пустой новый проект. Это соответствует session_state и stateless
архитектуре; ранее обещанного автосохранения нет, поэтому это ограничение,
а не нарушение существующего контракта.

Для многошагового составления такое поведение рискованно. Сейчас нет заметного
состояния «есть несохранённая работа», восстановления последней сессии или истории
резервных копий. Выбор защиты зависит от основного рабочего процесса и способа
размещения продукта; его нужно принять в интервью. Не выбирать БД/облако
по умолчанию до выяснения этого вопроса.

## Предложения аудитора перед интервью

1. **Подготовка вместо технического стартового экрана.** До первого поиска
   показать готовность состава, календаря, истории, отсутствий и закреплений.
   Для каждой проблемы дать следующее действие с переходом к нужным данным.
   Скрыть seed/имя solver в дополнительных настройках, если они не нужны
   составителю. На первом экране сейчас видны Seed, greedy/cpsat и сырое имя зоны.
2. **Диагностика с восстановлением.** Различать проблему данных, нехватку
   подходящих людей, подтверждаемое исключение и исчерпание поиска. Показывать
   сначала причины, которые пользователь может исправить, а не сотни следствий.
   Проверки ничего не ослабляют; готовность после исправления доказывается заново.
3. **What-if как решение, которое можно принять.** UI сейчас просит JSON patch,
   показывает таблицу разниц и не предлагает принять рассчитанный вариант в
   проект. Полезный сценарий: выбрать отпуск/сотрудника/настройку, увидеть эффект,
   принять выбранный график новой версией с сохранением исходного. Нужны явные
   правила сохранения pins и применения сценария; не подменять текущую версию
   автоматически.
4. **Осмысленные показатели.** Вместо необъяснённой σ/дробного баланса показать
   соблюдение нормы, покрытие, исключения, максимальную серию с границей месяца,
   одиночные выходные и наибольшую разницу нагрузки внутри подходящего пула.
   Долгосрочная справедливость не моделируется carry-over текущей структуры;
   окно в несколько месяцев — новая возможность, а не выполненное обещание.
5. **Чёткие границы Excel.** XLS умеет менять отображаемые смены и формулы;
   импорт поддерживает carry-over, а не весь исправленный рабочий проект.
   Индивидуальные часы находятся также в helper-таблице, поэтому произвольная
   внешняя правка текстового «День (Nч)» не является поддерживаемым пересчётом
   всех часов. Нужно определить, экспорт — финальная выдача или отдельное
   рабочее место с обратным импортом и разрешением конфликтов.
6. **Приёмка полезности.** Добавить независимый эталонный месячный сценарий с
   реалистичным сохранённым календарём и историей, без pins на все назначения.
   Пользователь должен пройти подготовку → расчёт → исправление → экспорт →
   восстановление и следующий месяц. Время/число ручных действий согласовать
   с владельцем; сейчас этот пользовательский бюджет не задан.

## Что действительно выдержало проверку

- Подмена status=ready не заменяет общую проверку: existing negative tests проходят.
- Подмена `DaySchedule.is_holiday` исправляется при проверке по полному календарю;
  эксперимент с ложным праздником на 01.04 дал нормализованный флаг false и
  корректный XLS helper=0. Первичная гипотеза о противоречии экспорта отвергнута.
- Ограничения отпусков, больничных, 5/2, отдыха после вечера, серий, пинов и точных
  часов проверяются отдельным validator; найденные UI ошибки его не отменяют.
- Датированная неизвестная история не подменяется молча нулём для ready.
- Проект сохраняет ручные назначения и месяцы; некорректный импорт атомарно
  сохраняет уже открытый проект. Проверены runtime и UI journeys.
- PDF экранирует данные и запрещает внешнюю загрузку ресурсов; XLS защищает строки
  от формул; API ZIP/filename обработка имеет security tests. Новая сетевая атака
  этим аудитом не обнаружена и отсутствие всех атак не утверждается.

## Порядок дальнейшей работы

Сначала PLOG-01–04: идентичность, сохранность истории и честная валидация входа.
Затем определение основного рабочего процесса и защита несохранённой работы.
После этого — понятная диагностика, применение сценариев, версия без шума и
объяснение качества. Порядок алгоритмических целей из интервью 004 сохраняется,
пока владелец явно не пересмотрит его.

Каждое исправление получит требования/приёмку в соответствующем живом контракте
или отдельном ограниченном изменении. Данный отчёт не разрешает реализацию
произвольного backlog и не объявляет существующие complete-контракты исправленными.
