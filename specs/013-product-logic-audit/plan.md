# План продуктового аудита

## Контекст и конституция

Python 3.12+, uv, существующий FastAPI/Streamlit продукт. Работа в dev без
feature-ветки, сохранение чужих изменений и прежних evidence. Контекст задаётся
SPECIFY_FEATURE_DIRECTORY=$PWD/specs/013-product-logic-audit и
SPECIFY_FEATURE_NO_PERSIST=1; feature.json не записывается.

## Порядок и решения

1. Сопоставить принятые продуктовые решения 004 и живые контракты 003–011 с
   источниками, действующими вызовами и тестами. Прочитать текущий Git/SHA.
2. Запустить существующую регрессию, UI journeys и независимые от сети
   экспериментальные проверки. Новый locked uv runtime находится в /tmp.
   Минимальные примеры и результаты сохранить в audit/evidence, без изменения
   кода приложения и без добавления зеркальных тестов документации.
3. Отделить подтверждённые дефекты от ограничений метода/контракта и возможностей
   продукта. Для каждой проблемы указать действие составителя и последствие.
4. Провести последовательное интервью по speckit-clarify: до пяти вопросов,
   каждый ответ фиксировать сразу; зависимые решения не принимать за владельца.
5. Уточнить живые контракты или создать ограниченные новые контракты. До каждого
   изменения за пределами SDD дополнить точный files scope. Сохранить ID, добавить
   новые задачи/приёмку; завершённые runtime-контракты не объявлять проверенными
   для новых требований. Будущую реализацию отделить от аудита.
6. Выполнить speckit-analyze, SDD --base HEAD, обновить generated index и проверить
   его. После завершения интервью и контрактов — проверки и обычная доставка
   в dev; продвижение в test/main не выполняется в этом этапе.

## Область и план после пяти ответов

Полный перечень 55 точных путей объявлен в traceability.json до изменения файлов.
Дополнены spec/plan/tasks/traceability/evidence живых 003, 006, 008, 009 и 010;
сохранены ID и исторические results, новые критерии вернули status в planned.
Уточнения владельца добавлены в specs/004-scheduling-validity/decisions.md;
проверенные текущие дефекты — в specs/000-baseline/gaps.md.

Созданы отдельные planned контракты: 014-product-reliability (5 требований),
015-guided-authoring (4), 016-stable-replanning (2), 017-two-month-quality (3).
Каждый имеет точный будущий code/test scope, собственный plan/tasks/traceability
и evidence о том, что реализация ещё не начата. Очередь по ответам владельца:
014 fixes → 015 подготовка/backup → 016 repair → 017 двухмесячное качество.
What-if применение вариантов остаётся более поздним предложением backlog.

PAUD-004 принимается документированными ответами/контрактами и содержательным
анализом, а не отсутствующими planned tests будущей реализации. PAUD-005 принимает
scoped/staged SDD, актуальный индекс, локальные checks и docs delivery в dev.

## Проверки и смысл traceability

Существующие tests проверяют затронутые области поведения и структурные gates.
Они не являются автоматическим доказательством качества аудита или интервью.
Основная приёмка PAUD-001/002 — матрица покрытия и воспроизводимые примеры;
PAUD-003/004 — ответы владельца и содержательное сопоставление контрактов;
PAUD-005 — фактические SDD/index и pytest результаты.

Команды: uv sync --locked --all-groups --extra solver; uv run --no-sync pytest
tests/ --ignore=tests/ui с coverage и JUnit; pytest tests/ui; минимальные
эксперименты TestClient/моделей/экспортов; check_sdd --base HEAD;
project_context --write/--check; Ruff/format/mypy при завершении поставки.

## Риски

Реальные производственные данные пока не предоставлены: проверенные синтетические
сценарии не доказывают частоту дефекта в команде владельца. UI визуальная проверка
и автоматические journeys не заменяют наблюдение реального составителя.
Публичные ответы API и календаря не проверяют внешнюю инфраструктуру доставки.
При отсутствии ответов интервью статус остаётся in-progress.
