# Ввод персонала до настройки состава

Дата: 2026-10-12. Статус: complete.
Основание: запрос владельца при приёмке test и короткое интервью.
Уточняет основной путь FLOW-001/FLOW-004 из
[015](../015-guided-authoring/spec.md) и UIC-001/UIC-005 из
[010](../010-ui-configuration/spec.md). Историческая приёмка сохраняется;
новое поведение проверяется отдельно по этому контракту.

## Цель и оценка

Реализовать стоит: сейчас _default_config в ui/components.py создаёт Config
из _DEFAULT_ROWS, а render_application сразу создаёт проект. Пользователь
редактирует демонстрационную команду вместо ввода своей. Шаг 0 отделяет
идентичность/город сотрудника от решения о его работе, уменьшает риск
случайного использования чужих имён и автоматически назначенных ролей.

## Пользовательские сценарии

### US1 — Внести реальный персонал (P1)

Новый проект начинается с шага 0 «Персонал»: два пустых многострочных списка,
Москва и Хабаровск. Составитель вводит или вставляет имена, по одному в строке;
видит количество по городам и общее число. После применения списка переходит
на шаг 1 «Состав» с теми же людьми, без подставленных ролей.

### US2 — Настроить работу персонала (P1)

Для каждого сотрудника независимо выбираются график «5/2»/«Гибкий» и участие
в дежурствах «Да»/«Нет». До явного выбора оба поля — «не настроено».
Можно выделить сотрудников и применить одно или оба поля сразу группе.
Итоги показывают по каждому городу всего, 5/2, гибкий, участвующих в дежурствах
и не полностью настроенных. Счётчики графика и участия независимы и могут
пересекаться: сумма «5/2» и «дежурит» не обязана равняться всему персоналу.

### US3 — Продолжить подготовку или открыть существующий проект (P1)

Применённый список и частичные назначения восстанавливаются после reload
в том же браузере. Открытие старого проекта/YAML сохраняет его персонал и
явные настройки; оно не заставляет вводить список заново. Ошибочный импорт
не уничтожает уже открытый проект или черновик подготовки.

## Требования и критерии приёмки

- **STAFF-001**: График и участие в дежурствах задаются независимо. Выбор 5/2
  не отключает дежурства сам по себе. Существующие hard rules, нормы, календарь,
  правила отдыха и проверки совместимости сохраняются. Приёмка: оба явных
  выбора сохраняются после открытия; запрещённые назначения не разрешаются
  новым способом ввода.
- **STAFF-002**: Новый проект начинается с пустых городских списков, без
  демонстрационных имён и автоматически назначенных ролей. Непустая строка
  задаёт сотрудника соответствующего города; внешние пробелы удаляются,
  внутренние символы и запятые сохраняются. Пустые строки пропускаются.
  Количество вычисляется автоматически. Пустой общий список и повторяющиеся
  имена после удаления внешних пробелов в любом городе отвергаются до
  применения с указанием причины; одинаковые имена не объединяются молча.
  Один город может быть пустым на шаге 0; нехватка дежурных проверяется позднее.
  Приёмка: ручной ввод/вставка, пустые строки, запятые, повтор внутри города
  и между городами; ошибочное применение сохраняет предыдущий черновик.
- **STAFF-003**: После шага 0 оба поля работы каждого сотрудника незаданы;
  персонал, имя и город видны на шаге 1. Индивидуальное/групповое назначение
  меняет только выбранных людей и явно заданные поля. Итоги по городам
  отражают независимые график/дежурства и количество незавершённых строк.
  Приёмка: частичное назначение, комбинация 5/2 + дежурства, пакетное изменение
  одного поля без сброса другого, корректные счётчики.
- **STAFF-004**: До полного задания обоих полей всем сотрудникам обычный расчёт,
  диапазон, repair и диагностический поиск не запускаются. UI показывает список
  ненастроенных сотрудников и недостающих полей. После выбора выполняются
  существующие проверки Config и готовности; нехватка подходящих дежурных
  не устраняется фиктивными людьми. Применение некорректного состава не
  заменяет рабочий проект, введённые данные доступны для исправления.
  Приёмка: spy поиска не вызывается для черновика; недостающие роли и нехватка
  команды объясняются; валидный состав проходит прежний путь подготовки.
- **STAFF-005**: Применённый черновик персонала и частичных ролей имеет устойчивые
  employee_id и сохраняется в том же браузере с теми же гарантиями failure,
  conflict и последнего корректного backup, что FLOW-002/003. При переносе
  в проект ID сохраняются; повторное применение и перестановка строк не
  создают новых ID для неизменённых сотрудников. Имя не является ключом
  идентичности после создания. Доступен резервный файл черновика; загрузка
  проверяется атомарно. Неприменённый текст формы обозначается отдельно и
  не обещается сохранённым. Приёмка: reload частичного состава, round-trip
  backup, отказ записи, повреждение, конфликт двух вкладок и стабильность ID.
- **STAFF-006**: Существующие project JSON и YAML открываются с прежними людьми,
  графиком, участием в дежурствах, ID, календарём, историей, pins и revisions;
  отсутствующий onboarding-маркер не сбрасывает их роли. Новый шаг обязателен
  для создания нового проекта; импорт валидного состава является альтернативой
  ручному вводу. Стартовый экран сохраняет доступ к восстановлению/импорту.
  Дальнейшие изменения применённого состава идут существующим путём
  update_config с прежней проверкой зависимостей. Массовая замена списков шага 0
  не является способом удаления людей из проекта с графиками.
  Приёмка: legacy JSON/YAML, импорт поверх черновика, неверный импорт,
  открытие готового проекта и сохранение неизменённой настройки без потерь.

## Совместимость и границы

Меняется старт нового проекта и UI подготовки; готовый Config/API/CLI и
алгоритмы планировщика сохраняют текущий контракт. Незаданные роли не кодируются
как employee.on_duty=False или автоматически выбранный schedule_type.
Черновик не является ScheduleProject/Config и не может быть ready.
Browser autosave расширяется для черновика с различимым типом/версией и
совместимым чтением прежнего формата; неизвестные форматы отвергаются явно.
Демонстрационные данные допустимы в примерах/fixtures, но не как стартовый состав.
Общий каталог персонала между проектами, аккаунты, синхронизация устройств,
новые города, новые бизнес-роли и применение what-if не входят в изменение.
Повторяющиеся отображаемые имена требуют отдельного изменения существующей
совместимости, а не неявного объединения в этом шаге.
