# Предсказуемое исправление существующего месяца

Дата: 2026-10-11. Статус: in-progress. Основание: ответ 3 интервью 013, PLOG-08.

## Пользовательские сценарии

### US1 — Исправить график без лишних перестановок (P1)

После изменения ограничений составитель пересчитывает уже существующий месяц.
Алгоритм сохраняет как можно больше допустимых назначений. Исходная версия
доступна для сравнения; полный пересчёт остаётся явным отдельным действием.

## Требования и критерии приёмки

- **REPAIR-001**: Default пересчёта существующего месяца использует текущую версию
  как baseline. После выполнения hard rules, выбранных часов, pins и подтверждений
  минимизируется число изменённых employee-day ячеек; затем применяется действующий
  порядок качества. Ячейка изменена при смене состояния или рабочих часов, одно
  изменение пары считается один раз. Смена имени при неизменном ID не считается
  перестановкой. Существующие допустимые ячейки не превращаются автоматически
  в постоянные pins. При отсутствии baseline выполняется обычный первый расчёт.
  Конфликт пина с запретом возвращает диагностику и не снимает pin молча.
- **REPAIR-002**: Исходная версия сохраняется, результат содержит baseline ID,
  число/список правок, status поиска и доступное доказательство оптимальности.
  Feasible/timeout/heuristic не называют глобальным минимумом. При неизменённом
  ready baseline пересчёт сохраняет назначения; повторная check_current не создаёт
  новую ревизию назначений при том же входе/результате, но запись проверки допустима
  отдельно. Неуспешный repair не заменяет исходную текущую версию без явного
  применения диагностического черновика. Полный пересчёт явно выбирается пользователем.

## Совместимость и границы

Уточняется REV-001/REV-003 и порядок качества существующей версии. Для первого
расчёта согласованный порядок HOURS-004 сохраняется; у repair минимизация
перестановок предшествует мягкому качеству и не отменяет hard rules.
Публичный generate(Config) сохраняет работу без baseline. Переносы зависимых
месяцев по-прежнему инвалидируются реальными изменениями, а не no-op проверкой.
Нет нового самостоятельного утверждения всего графика или назначения ролей.

## Приёмка

Готовый unchanged baseline, изменение одной недоступности с известным небольшим
repair, часы Р, конфликт pin, rename и failed search. Для малого fixture с полным
перебором проверяется реально минимальное число правок; для bounded большого
входа проверяются допустимость, metadata и отсутствие ложной гарантии.
